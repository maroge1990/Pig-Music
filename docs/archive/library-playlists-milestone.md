## Plex and live publication

Plex runs at `192.168.1.233:32400`, with Music section 3 and `/Audio` mapped to the same Synology share. Its existing server credential was used privately for testing; no token is returned by the app's public status endpoint. A disposable native Plex playlist was created, updated in order, verified and removed. Existing playlists were untouched.

Sync owns only playlists with a durable Pig Music identity and ownership marker. It maps exact indexed file paths, publishes the available subset and retries every minute. Missing songs stay in Pig Music until their files are published and indexed. Plex's native API removes repeated rating keys: Pig Music retains repeats, while Plex receives first-occurrence order. The deployed connection is **enabled**. The user assigned LAN address `192.168.1.203`; an ARP duplicate-address check received no replies before attachment. Pig Music is attached to Unraid `br0` with that static IP and retains its bridge network as the default gateway (`br0` gateway priority -1). Plex identity and MusicBrainz were reachable from the running container. Favourites was created in the real Plex server: all 17 available file paths and their order were verified against Pig Music, with 71 entries pending. No other playlists were edited. The new LAN URL works; the former host-published LAN URL times out due to asymmetric routing after the LAN attachment. Tailscale access after this network change has not been verified. Both network attachments are saved in the deployed Compose configuration; future update helpers must preserve them instead of recreating a bridge-only container.

NAS publication and replacement safeguards are implemented but **disabled**. The mount is still read-only. See [the concrete publication proposal](proposed-nas-publication.md). Its 13 current destinations have no collisions. Runtime publication requires an explicitly enabled deployment configuration and a matching NAS ownership marker. NAS hard-link support, permissions, real Plex indexing and restore operations still need acceptance on the actual share before enabling writes.

The old Lidarr, Soularr, slskd and Music Grabber containers have **not been removed**. Artist-wide acquisition, optional monitoring, general removal/restore, and review/apply of existing naming/tagging changes are still outstanding phase 1 acceptance items. The current implementation is independent for scanning, metadata, source adapters, queueing and tested acquisition; it is not full Lidarr feature parity. Retirement is reserved for the live-library cutover and independence acceptance, with retained configuration/appdata backups.
