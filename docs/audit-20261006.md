# Pig Music audit: brand, artwork speed and scale readiness

Review date: 6 October 2026. Scope: the full `Pig-Music` repository (server, client, deployment), checked against the Pig family brand standard 1.0 in `Pig-Branding`. Priority focus: consistency of brand application, artwork and graphical performance, and readiness for **two users with 10k–50k tracks each**. The future Swift and watchOS clients got a light-touch review only.

This is a review. It made no code changes and touched no live services.

## Prioritised findings

Priority key: **P0** blocks the 10k–50k target or risks failure; **P1** is high value and should follow the next milestone; **P2** is worthwhile polish or structure; **P3** is opportunistic. Each finding gives its evidence, then a recommendation.

### P0: must fix before libraries grow

**P0-1. Embedded cover art is stored as base64 inside `library-snapshot.json`.**
The scanner puts every embedded or folder image (up to 5 MB each) into the snapshot's `covers` map as base64 (`server/scanner.py:233-237`). The snapshot is then fully parsed on every `refresh_library()` (`server/store.py:65`) and fully re-read and rewritten on every scan (`server/scanner.py:166-260`). At 10k tracks the snapshot reached 378 MB and peak memory reached 1.17 GB, which is over the container's 1 GB limit. At 50k tracks it would be about 1.9 GB on disk, so the container would OOM. The live 1,395-track snapshot is already 20.6 MB, which the cleanup review flagged, and this is the main cause. `refresh_library()` runs after exports, organisation, recovery and settings saves. A multi-hundred-MB `json.loads` holds the GIL even inside `to_thread`, so the whole API stalls while it runs.
→ At scan time, write each cover once to a **content-addressed file** (`covers/<sha256>.jpg`, normalised at scan) and store only the hash in the snapshot. Keep the snapshot to metadata only. Add a one-off migration that extracts existing `covers` entries, plus a regression test that asserts the snapshot has no image bytes.

**P0-2. Cover identity is wrong for editions and never refreshes.**
`cover_key = album_artist + "\x1f" + album` (`server/library.py:139`) ignores the edition split the cleanup introduced, so deluxe and standard editions share one image. `_cache_covers` skips work when the target file exists (`server/store.py:838`), so retagged art is never picked up. The scanner also keeps old `covers` entries forever, and nothing prunes orphaned files in `covers/` or the per-album `missing-artwork:*` and `catalogue:*` rows in `documents`.
→ Key covers by content hash (fixes refresh and dedupe for free) and attach the hash per album edition. Add a periodic, safe prune of unreferenced cover files and expired negative-cache documents.

**P0-3. Cold artwork requests can freeze the rest of the UI.**
`/api/library-artwork/...` does the whole MusicBrainz search, Cover Art Archive or Fanart fetch, and resize *inside the image request* (`server/app.py:440-470`, `server/artwork.py:79-160`). The catalogue limiter serialises those lookups to roughly one per second. Uvicorn serves HTTP/1.1, where browsers allow about 6 connections per origin, so a grid of uncached tiles holds every connection. Search, queue and navigation requests then wait behind image requests. Artist tiles are worse: with portraits on, every artist's `cover_url` points at the portrait route (`server/store.py:870-873`), which looks up by **name** (`portraits.get(app.state.http, item["name"])`). That forces an extra MusicBrainz artist search per artist before Fanart.
→ Never block an image request on the network. Return the best local image immediately (an album cover is always better than nothing), or a 404 so the placeholder shows, and queue the enrichment in the background. The client picks up the improved art on the next library revision. Pass the known MusicBrainz artist ID when you have it. Optionally put Pig Music behind `tailscale serve` or Caddy with HTTPS, which gives HTTP/2 multiplexing (and helps the Swift client, see F-1).

### P1: artwork speed and the brand fundamentals

**P1-1. Only one image size (512 px JPEG) is served everywhere.**
Album and artist tiles render at about 107–200 CSS px. The 375 px phone grid is about 107 px, or 214 device px at 2×, so tiles download 2–5× the pixels they need. The same 512 px file is used for the 1600×900 hero cover and the now-playing art (soft on retina). The watch will want about 100–200 px. In the local check each tile was about 140 KB, a worst case for noisy synthetic art; real art usually runs 40–90 KB.
→ When a cover is first cached, generate derivatives (for example 128, 256, 512 and 1024) in **WebP, or AVIF with a JPEG fallback**. Expose them as `/api/artwork/<hash>?w=256` or as fixed path variants, and use `srcset`/`sizes` in `Cover.tsx`. The same size ladder will serve the iPhone and Watch clients.

**P1-2. Artwork and static assets don't have strong cache headers.**
`/api/artwork/*` (StaticFiles) sends ETag and Last-Modified but **no `Cache-Control`**. The library and catalogue artist portrait and background routes send `no-cache` (`server/app.py:464`, `904`, `918`). Every view therefore revalidates every tile (16 conditional 304 requests on one phone screen locally), and the portrait route reruns `portraits.get()`, which reads the settings file, hashes the key and queries SQLite, before it can answer. Hashed `/assets/*` bundles are not marked immutable.
→ Once URLs are content-addressed (P0-1), send `public, max-age=31536000, immutable` for artwork and `/assets`. Version portrait and background URLs (for example `?v=<hash>`) so `no-cache` is no longer needed.

**P1-3. Small type is used widely, and the web stylesheet is pixel-locked.**
`styles.css` sets text at 9 px 27 times, at 8 px 13 times, and also at 7 px and 6 px (brand subtitle, `:170`, `:1315`). On the 375 px library view, the bottom navigation labels and counts compute to **9 px** and the tab chips to 10 px. Every size is in `px`, so text ignores the user's browser or OS text-size setting. The brand standard asks for native type with Dynamic Type, or Inter/system on the web. This is also the largest consistency gap the future Swift client will expose, because it will use Dynamic Type sizes.
→ Define a type scale as tokens in `rem` (for example 12/13/15/17/20/28/34, aligned with the iOS text styles) with an 11–12 px minimum. Replace the 29 distinct font sizes with those roles. Check the phone layout at 200% text size.

**P1-4. No shared Pig Music wordmark, home-screen icon or manifest.**
The sidebar and mobile header render "Pig Music" as live Inter text (weight 750). The standard says to *"use supplied light/dark wordmark artwork"*. The blueprint rightly forbids reusing PigTV lettering, but no Pig Music artwork exists yet. `index.html` has no `apple-touch-icon` and no web manifest, so "Add to Home Screen" on iPhone produces a screenshot icon, even though Pig-Branding already ships 1024 px light, dark and tinted icons. The favicon is the non-square 256×204 pig.
→ Have Pig-Branding generate Pig Music wordmarks with the same Swift generator (`Tools/make-brand-assets.swift`) used for PigTV, plus square icons. Add `apple-touch-icon`, a `manifest.webmanifest` and a square favicon. The Swift and watch clients will need the same assets, so produce them once.

**P1-5. Tokens are hand-copied, and the player uses three unapproved colours.**
The CSS custom properties match `brand-tokens.json` today, but only because they were copied by hand. Nothing checks for drift, and the same copying will happen again for Swift. The protected player surface adds `--secondary: #d9d2dd`, `--control-border: #8c7f95` and `--border: #493d52` (`styles.css:2839-2848`). None of these are approved tokens, and the standard requires new colours to be reviewed. The player surface uses dark `surface` (#1E1925) rather than the `media.solidPanel` token (#15111A). Shadows and the modal scrim use untokenised hex-alpha values (`#0004`, `#000b`, and so on).
→ Add a small script, in Pig-Branding or here, that **generates `tokens.css` (and later a Swift asset catalog) from `brand-tokens.json`**, plus a test that fails on drift. Either get the three player values approved as `media.*` tokens or replace them with existing roles. Add `shadow` and `scrim` tokens.

**P1-6. Serialised and blocking image work on the server.**
- `Backgrounds` uses **one global lock** for every artist (`server/artist_backgrounds.py:17,33`), so one slow Fanart download blocks every hero backdrop. Use per-key locks like `Artwork` and `Portraits` already do.
- `Portraits.get` calls `self.artwork.save(...)` **synchronously on the event loop** (`server/portraits.py:131`). PIL decode and resize stall all requests. Use `asyncio.to_thread` as `artwork.py` does.
- `_cache_covers` decodes every new cover inside `refresh_library` under `library_lock` (7.9 s at 10k on first refresh). This goes away with P0-1.

**P1-7. `/api/library` returns the whole library in one uncompressed response, and grids aren't virtualised.**
The payload is 2.0 MB at 50k tracks with no gzip (no `GZipMiddleware`) and `no-store`, and it is refetched on many actions (`main.tsx:297,347,523,541,1742`). The artist and album grids render every item (`main.tsx:998`), about 5,000 album cards at 50k tracks. Lazy images help bandwidth but not DOM or layout cost on a phone.
→ Add GZip or Brotli compression (roughly a 10× saving on this JSON). Serve `/api/library` with `ETag: <revision>` and honour `If-None-Match`. In the grids, use `content-visibility: auto` on cards (cheap) or windowing (thorough), and consider paging albums per tab.

### P2: structure, consistency and smaller performance wins

**P2-1. Linear lookups on hot paths.** `next(i for i in store.library[kind] if i["id"] == item_id)` appears in the artwork, album and artist routes (`server/app.py:156`, `174`, `444`, `472`, `496`, `787`) and in `categorise`. Build `albums_by_id` and `artists_by_id` dictionaries in `_refresh_library`.

**P2-2. Settings are re-read from disk on every call.** `media.settings()` loads `media-settings.json` on every invocation. That includes once per artist inside `_cache_covers` (`store.py:870`) and once per portrait or background request. `ArtistHero` also fetches `/api/settings/media` on every artist view before it can request the backdrop, which adds a waterfall step. Cache the settings in memory, invalidate on save, and include `fanart_configured`/`portraits` in the library summary.

**P2-3. Hero backdrop cost on phones.** Each artist view loads the 1600×900 backdrop twice (sharp and soft layers, `ArtistHero.tsx:92-103`) and blurs it with CSS. Serve a phone-sized derivative (P1-1) and a tiny pre-blurred version for the soft layer. Store a **dominant colour or BlurHash** for each cover and backdrop when caching them. The UI can then paint an on-brand placeholder instantly, and Swift and watchOS can use the same metadata.

**P2-4. The catalogue artist-artwork fallback redirects to coverartarchive.org** (`server/app.py:939`). That bypasses the server cache, exposes the client's IP to a third party, and is slow on a phone. Route it through `artwork.catalogue_cover`.

**P2-5. The preload loop scales poorly.** Every 15 minutes it walks every artist (`server/app.py:812-856`) and issues catalogue, portrait, background and three cover lookups per artist. Once the daily cache expires, 1,000+ artists means hours of rate-limited background traffic competing with the foreground. Make it incremental: process only new or changed artists, and back off on known-missing items.

**P2-6. Spacing and radius drift from the vocabulary.** Radii in use include 3, 4, 5, 8 and 12 px alongside the approved 6/10/16 px and capsule. There are about 20 off-scale spacing values (5, 7, 9, 13, 15, 22, 25 px and so on). The standard explicitly says not to change density just to hit numbers, so treat this as tokenising, not restyling: add `--radius-compact/card/hero/capsule` and `--space-*` variables and migrate opportunistically.

**P2-7. Stylesheet and component hygiene.** `.brand-mark` is defined twice (`styles.css:149` and `:1783`), and `.brand-mark svg` is dead. The legacy aliases (`--muted`, `--line`, `--green`, `--panel`) should be removed. `main.tsx` (2,054 lines) and `styles.css` (2,922 lines) are monoliths. Split views such as Library, Album, Artist, Queue and Settings into components with co-located styles, which makes brand audits and Swift parity mapping far easier. The same applies to `server/app.py` (1,174 lines) and `server/store.py` (1,192 lines): use FastAPI routers per area.

**P2-8. Library tabs wrap on a 375 px phone.** "Favourites" drops to a second row beside the sort control. Make the chip row a single horizontally scrollable row, or move sort beneath it.

**P2-9. Placeholder art isn't branded.** Missing covers show a generic `Disc3` icon plus initials. A brand-aligned placeholder (raised surface, accent initials, or a dominant colour from P2-3) would look less like broken images, especially while P0-3 enrichment is pending.

**P2-10. Polling.** The queue polls every 5 s and Soulseek health every 15 s. Expose a server-sent events (SSE) stream for `library_revision`, queue changes and health. The web client gets instant updates without polling, and the same stream is the natural change feed for the Swift client.

### P3: minor or opportunistic

- The "in library" tick on every card in *Your library › Artists* is a status symbol, not a selection (so it's allowed by the standard), but on that view it repeats on every card and adds little. Consider showing it only in mixed (discover/search) contexts.
- The `/assets` bundle is a single 313 KB chunk. Split rarely used views (Organisation, Recovery, Import) with `lazy()` to speed the first load over Tailscale.
- `fastapi.testclient` emits a deprecation warning under the current Starlette; pin or migrate before it becomes an error.
- Cross-origin write protection relies on the `Origin` header, so clients that send none (curl, native) bypass it. That's acceptable on a private tailnet today, but see F-2.

## Future features and readiness (light touch)

**F-1. Swift and watchOS clients (P01/P02).** These are foundations to put in place before starting native work, not blockers today:
- **API contract:** version the routes (`/api/v1`), publish the FastAPI OpenAPI schema, and freeze response shapes the native app depends on (library, album, artist, playback, artwork).
- **Artwork:** the size ladder and content hashes (P0-1, P1-1) let the phone and watch cache artwork by hash forever and request watch-sized images.
- **Change feed:** `library_revision` already exists. Pair it with SSE (P2-10) and a "changes since revision" endpoint for offline sync.
- **Offline audio for Watch:** the blueprint's rule is never to transcode to obtain a *library* quality. Whether the watch may carry **device-side derivative copies** (for example AAC 256 for storage) is a separate decision for the owner. Record it before P02 design.
- **Transport:** run HTTPS via `tailscale serve`. It gives HTTP/2, satisfies iOS App Transport Security, and provides tailnet identity headers.

**F-2. Two users (H01/H02).** Tailscale identity (`Tailscale-User-Login` via `tailscale serve`) can provide per-user scoping without adding public auth, which is consistent with the blueprint's "no new authentication assumptions". Decide on it alongside the H01 design. With content-addressed covers, both libraries share one artwork cache.

**F-3. Brand-system enhancements.**
- **Single source of truth:** generate CSS, Swift asset catalogs and watch complication colours from `brand-tokens.json` (extends P1-5).
- **Now-playing accent:** a per-artwork accent derived from the dominant colour, constrained to the protected dark player and keeping the rose accent for controls. This needs brand review, because any new colour treatment does.
- **Branded empty and welcome states:** use a large pig crop with the approved soft halo, which the standard explicitly permits.

**F-4. Other ideas that fit the roadmap.**
- An artwork fix-up tool: pick or replace a cover from CAA candidates per edition, display-only so tags aren't touched (consistent with the artwork module's contract).
- A "recently added" shelf, driven by the revision feed.
- Per-user listening history, which would feed popularity and Shazam inbox work (S01).
